## Context

当前 HabitPulse 应用支持手动创建习惯，用户需要逐个填写名称、重复周期、提醒时间、重复星期等字段。AI 创建习惯功能旨在通过自然语言交互，让用户描述习惯后由 AI 解析意图并引导完善信息，最终批量创建习惯。

项目约束：
- 使用 Kotlin + Jetpack Compose + Material Design 3
- Room 数据库存储习惯数据
- DataStore 存储用户偏好设置
- 单 Activity 架构，Navigation Compose 导航

## Goals / Non-Goals

**Goals:**
- 实现基于 LLM 的对话式习惯创建流程
- 支持配置自定义 API 端点、密钥、模型（兼容 OpenAI 格式）
- 支持多种问题类型（时间、星期、单选、多选、确认、文本）
- 实现安全守卫（死循环检测、问题上限）
- UI 支持中文/英文跟随用户语言

**Non-Goals:**
- 不实现离线缓存对话（每次进入是新对话）
- 不实现 AI 建议习惯功能（后续扩展）
- 不实现 AI 编辑已创建习惯（后续扩展）
- 不支持语音输入（后续扩展）

## Decisions

### 1. 工具调用方案：不使用 Function Calling，采用 Markdown 代码块

**决策**: 使用 Markdown 代码块包裹 JSON 指令，而非 LLM 原生 Function Calling。

**理由**:
- 兼容性更强：支持智谱 GLM、DeepSeek 等多种兼容 OpenAI 的 API
- 实现简单：只需正则解析代码块，无需处理 Function Calling 协议
- 易于调试：输出格式清晰可见

**替代方案考虑**:
- Function Calling：需要模型支持，部分模型不支持或支持不稳定

### 2. 对话状态管理：单次对话，不持久化

**决策**: 不保存对话历史到磁盘，每次进入 AI 创建界面都是新对话。

**理由**:
- 简化实现：无需处理状态持久化、恢复逻辑
- 用户场景匹配：习惯创建是短时操作，不需要跨会话
- 减少存储：对话数据不需要长期保留

### 3. 问题组件渲染：每个 type 对应独立 Composable

**决策**: 每个问题类型（choice、time、day_of_week 等）对应独立的 Compose 函数。

**理由**:
- 代码组织清晰：每个组件独立，便于维护
- 复用方便：组件可以在其他场景复用
- 测试友好：每个组件可以独立测试

### 4. 习惯保存时机：确认阶段批量保存

**决策**: AI 解析完成后显示确认对话框，用户确认才保存到数据库。

**理由**:
- 安全：防止 AI 错误创建习惯，必须用户确认
- 可编辑：确认前可以编辑或取消某些习惯

### 5. 路由方案：复用现有 HabitCreationScreen

**决策**: 复用 HabitCreationScreen 接收 prefill 参数，支持从确认卡片跳转编辑。

**理由**:
- 减少代码重复：无需新建编辑页面
- 体验一致：编辑体验与创建体验相同
- 实现简单：只需添加参数解析逻辑

### 6. AI 设置页面：独立子页面

**决策**: AI 设置作为 Settings 的子页面（通过 NavigationLink 跳转），而非设置页面的一个区块。

**理由**:
- 功能隔离：AI 配置相对复杂，独立页面更清晰
- 符合现有设计：SettingsActivity 已使用子页面结构
- 可扩展：后续 AI 相关设置可以添加到此页面

**UI 细化的交互要求**:
- AICreateHabitScreen 的 AppBar 右上角有设置图标，点击跳转 AI 设置
- AI 设置是 Settings 的子一级菜单
- AI 设置界面**实时保存**（输入即保存）
- 从 AI 设置返回后显示 Toast 提示"已保存"
- 输入框有内容时右侧显示清除图标（点击快速清空）
- API 密钥输入框有显示/隐藏密码切换按钮
- 所有输入框有最大长度限制（端点 200，密钥 100，模型 50）

### 7. API 兼容方案：兼容 OpenAI 格式

**决策**: 支持配置自定义 API 端点和模型名称，默认使用智谱 glm-4.7-flash。

**理由**:
- 默认智谱：glm-4.7-flash 是免费模型，适合大多数用户
- 兼容 OpenAI：用户可以配置其他兼容 OpenAI 的 API（如 DeepSeek）
- 灵活性：用户可以自建支持 OpenAI 格式的 API

**API 请求格式**（基于智谱文档）:
- 端点: `{customEndpoint}/chat/completions`
- 方法: POST
- Headers: `Authorization: Bearer {apiKey}`, `Content-Type: application/json`
- Body:
  ```json
  {
    "model": "glm-4.7-flash",
    "messages": [...],
    "stream": false,
    "temperature": 0.7,
    "max_tokens": 4096
  }
  ```

**支持模型列表**（预设选项）:
- `glm-4.7-flash` (默认)
- `glm-4-flash`
- `glm-4`
- `glm-3-flash`

### 8. AI 创建习惯界面 UI 规范

**界面布局**:
- 整体模仿 DeepSeek 移动端设计
- 底部输入框区域

**输入框规范**:
- 空状态：显示 3 行高度
- 有 1-3 行文本：显示当前行数高度
- 有 3 行以上文本：显示实际行数高度
- 超过 7 行：最多显示 7 行（可滚动）

**发送/停止按钮**:
- 用户输入后显示"发送"按钮
- AI 输出中显示"停止"按钮

**AI 输出规范**:
- 流式输出：先显示原始文本（逐字或逐词）
- 完整代码块：检测到完整代码块后，渲染对应的 UI 组件

**聊天布局**:
- 左侧：AI 输出（气泡样式）
- 右侧：用户输入（气泡样式）

**欢迎语**:
- 未开始聊天时：大文本显示欢迎话语

**清空对话**:
- AI 有输出后，输入框上方显示清空对话按钮
- 点击后弹出确认对话框

**退出确认**:
- 退出 AI 创建界面返回时：询问是否确认离开（变动不保存）
- 进入 AI 设置时：询问是否确认离开

**会话不保留**:
- 退出后再进入：不保留之前的对话记录（新对话）

## Risks / Trade-offs

| 风险 | 描述 | 缓解措施 |
|------|------|----------|
| LLM 输出格式不稳定 | 模型可能输出非标准格式的代码块 | 重试机制 + 格式纠正提示 |
| API 配置复杂 | 用户可能不清楚如何获取 API Key | 设置页面提供清晰的配置说明和默认值 |
| 无限循环 | AI 可能陷入重复提问 | 死循环检测守卫（连续相同问题≥3 次强制停止） |
| UI 线程阻塞 | 网络请求可能在主线程 | 使用 Coroutines + Flow 处理异步操作 |
| 屏幕旋转丢失状态 | 配置变更导致 ViewModel 重建 | 使用 remember + 保存的状态恢复 |

## 强制任务完成检测机制（Decision #9）

**决策**: 任务开始时从用户描述中提取习惯数量，并强制 AI 收集完所有习惯后才能进入确认阶段。

**流程**:

```
用户: "帮我创建两个习惯：每天跑步、每周读书"
  ↓
系统提取数量 → pendingHabitCount = 2
  ↓
AI 问跑步习惯 → 用户回答 → AI 调用 create_habit (1/2)
  ↓
AI 问读书习惯 → 用户回答 → AI 调用 create_habit (2/2)
  ↓
系统检测到已收集 N 个 → 显示批量确认对话框
```

**强制干预规则**:

- AI 提前输出 `confirm`：系统检测到收集数 < pendingHabitCount → 发送修正消息给 AI，错误 confirm 不渲染
- AI 未调用 `create_habit` 但输出 `confirm`：视为提前触发，同样干预
- AI 在对话过程中遗漏某个习惯：用户可以追加描述，系统追加 pendingHabitCount

**兜底回复机制**:

- 用户输入不含习惯相关关键词 → 发送兜底 reply 消息，不提取/不创建习惯
- 兜底 reply 最大长度 50 词（功能用法）/ 30 词（闲聊重定向）
